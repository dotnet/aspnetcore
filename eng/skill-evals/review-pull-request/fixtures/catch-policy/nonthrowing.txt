Selected scenario
Construct ConversationEngine with FailingClient and RecordingDiagnosticSink.
Register StatusObserver.OnStatusChanged, then await SendMessageAsync.
These are the only implementations in scope for this bounded scenario.
ThrowingDiagnosticSink is not registered, selected, or called in this scenario.

Originating issue
Report conversation-processing failures through the configured diagnostic sink.

Target-base contract
Processing failures are exposed in Error and the Error status.
If the configured diagnostic sink fails during error reporting, the returned task
must fault with that sink failure. This applies to newly introduced reporting call
sites as well as existing ones.

PR rationale and test
The author says the nested catch preserves successful task completion.
A new test awaits SendMessageAsync and asserts that Error is the client's Failure.
Its complete implementation is in ConversationEngineTests.cs.source. That separate
test configures ThrowingDiagnosticSink, not the RecordingDiagnosticSink selected
above. It is not evidence that the throwing sink is selected in this scenario.
